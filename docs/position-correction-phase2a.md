# Position Correction Phase 2A: Main-decoupled prediction contract

Phase 2A defines a **boundary only**. It adds no HIP predictor algorithm, position learner, offset, pelvis/root constraint, IK writeback, or visible-output path. `PositionPrediction` is derived model data, not a `PoseObservation` and not an independent absolute measurement. No Phase 2A object is registered with `ConstraintPipeline` or passed to `ConstraintIkWriteback`, `OutputContinuityController`, or SteamVR output.

## Why the boundary is separate

The current computed HIP is downstream of `ConstraintIkWriteback`: Main FULL position can enter `HumanSkeleton` and then the same computed HIP. Learning `p_main - p_computedHip` and feeding that error back into the solver would create a circular, potentially double-applied correction. `BackgroundIkPoseReader` reads that post-IK tracker; `OutputPose` is still farther downstream. None is a position-correction teacher. `HipRotationCorrection` uses raw assigned observations, but its corrected IMU orientation contains Main-derived information and is not automatically a Main-decoupled position input.

The future `MainDecoupledHipPredictor` accepts only copied `RawHmdPoseInput`, `RawImuOrientationInput`, `BodyModelIdentity`, `FixedCalibrationIdentity`, an exact `CoordinateSpace`, assignment generation, and monotonic time. It does **not** accept `HumanSkeleton`, `HumanPoseManager`, mutable `Tracker`, `EffectiveConstraint`, `ResolvedTrackingPose`, computed trackers, `BackgroundIkPose`, or `OutputPose`. Main observations are absent from the predictor input. An external SteamVR HMD can be marked `isComputed=true` by the existing bridge, so that flag alone cannot classify it as a solver output. A future trusted ingress adapter must establish `RAW_HMD` from origin and `isHmd`, reject internal/output sources, and supply genuine local physical position-sample provenance. Phase 2A does not invent that provenance.

The current body dimensions live in a mutable `SkeletonConfigManager`; there is no verified immutable model-parameter snapshot with an epoch. `BodyModelIdentity` is therefore opaque. A later phase must define an immutable, versioned body-model snapshot before implementing the predictor. This is why no runtime provider seam is added now. A fake predictor in tests returns a fixed vector; it does not read computed HIP.

## Prediction, time, frame, and epoch

An AVAILABLE `PositionPrediction` requires a finite position, explicit exact space, known body reference, valid provenance, and nonempty lineage. UNAVAILABLE has a null position; `(0,0,0)` remains a legitimate available value. `HIP_CENTER` and `TRACKER_MOUNT` are distinct body references. A raw Main tracker mounting point cannot be compared to a HIP-center prediction until its tracker-to-body transform has been confirmed; an unknown Main reference fails closed. Exact `CoordinateSpace` equality includes ID, convention, and revision. An operator assertion such as `confirmed_same_space` does not prove physical calibration.

`PositionPredictionProvenance` separates `generatedAtNanos` from the physical input support window `[inputEarliestAtNanos, inputLatestAtNanos]`. All three are in Monaka's local monotonic domain; `generatedAtNanos` is **not** substituted for a physical sample time. The window must be ordered and no later than generation. The prediction epoch carries HMD and IMU source identities and reconnect epochs, IMU calibration epoch, body-model epoch, fixed-calibration epoch, exact coordinate space, and assignment generation. A numerically identical prediction from a changed epoch is a different lineage.

Lineage names raw HMD, raw IMU, body model, and fixed calibration. The centralized `PositionCorrectionTeacherEligibility` preflight rejects Main observation, resolved Main, IK constraint, computed tracker, Background IK, visible output, and Direct output dependencies. It also rejects `ROTATION_CORRECTION` by default because Phase 1 `q_corr` was learned from Main orientation; its effect on future position-learning feedback has not been reviewed. The allowed raw lineage must explicitly include HMD, IMU, body model, and fixed calibration. Source identity validation reuses the `monaka-direct:`, `monaka-solver:`, `monaka-private:`, and `human://` exclusions.

The future `PositionCorrectionInput` keeps the raw normalized Main backend observation in a separate field from the prediction. Its preflight requires usable finite Main position and provenance, trusted raw-backend origin, exact space, matching known body reference, current prediction epoch and assignment generation, and nonfuture timestamps. Passing preflight means **eligible for temporal pairing**, not permission to learn: Phase 2B still must specify the pairing window and correction law. No `p_main - p_prediction` calculation occurs in Phase 2A.

Core tests exercise the safe lineage and each forbidden dependency, source namespaces and computed identities, NaN/Inf/unknown validity, support-window ordering, exact space and body reference, future timestamps, and every epoch component. Existing Rotation Correction, Hybrid stress, diagnostics, continuity, and MTP E2E suites remain the software regression gate. Hardware/HIL and SteamVR interactive validation: **NOT RUN**.
